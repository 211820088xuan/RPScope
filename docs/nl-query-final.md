### 优化前各阶段占比

|---|---|---|---|---|---|
| Q1 | 0% | 67% | 0% | 0% | 99% |

| Q6 | 0% | 82% | 0% | 0% | 100% |
| Q7 | 0% | 10% | 0% | 49% | 100% |

**瓶颈：槽位抽取 LLM 占 49-82%，回答生成 LLM 占 93-126%。** 模板执行 <100ms，分类/链接 ~0ms。

### 规则槽位抽取优化

为 Q1-Q6 写模式匹配槽位抽取器（`src/query/rule_slots.py`）：
- Q1: 正则提取 6 位代码 / 公司名
- Q2: 双代码 / 双中文实体名
- Q3: 人名（2-4 字 + "控制/持有/担任"）/ 公司名
- Q4: 代码/公司名 + 角色关键词映射
- Q5: 代码/公司名 + 事件类型关键词映射
- Q6: 双代码 / 双公司名

规则抽取成功则不调 LLM，失败走 LLM 兜底。

| Q2 | 10s | 5.7s | 1.8x | 回答生成 LLM |
| Q3 | 8.6s | 2.9s | 3.0x | 回答生成 LLM |
| Q4 | 18.7s | 6.7s | 2.8x | 回答生成 LLM |
| Q5 | 13s | 4.0s | 3.3x | 回答生成 LLM |

### 不可消除的延迟

- **回答生成 LLM**：Q1-Q6 剩余 2.5-6.7s 全部来自回答生成，这是 LLM 生成自然语言的固有延迟，无法用规则替代
- **Q7 SQL 生成 + 回答生成**：两次 LLM 调用，P50 33s，结构上无法避免
- **模型响应波动**：P50 vs P95 差距来自 deepseek-v4-flash 的响应时间波动（网络+排队），非系统问题

## T4 — 架构说明

### 模板路径 vs 模板外路径

| 路径 | 意图 | 执行方式 | 数据源 |
|---|---|---|---|
| 模板路径 | Q1/Q2/Q6 | 规则引擎 R1-R7 + 图遍历 | networkx 图 (graph.pkl) |
| 模板路径 | Q3/Q4/Q5 | SQL 查询 | SQLite 事实源 (rpscope.db) |
| 模板外路径 | Q7 | LLM 生成 SQL + 三道校验 | SQLite 事实源 (rpscope.db) |

**数据一致性**：图 (graph.pkl) 由 SQLite 事实源重建（`scripts/rebuild_graph.py`），两者数据一致。Q1/Q2/Q6 走图遍历是因为关联方判定逻辑 (R1-R7) 实现在图层；Q3/Q4/Q5 走 SQL 是因为直接查事实源表更快。Q7 生成 SQL 而非图查询，是因为 SQL 结构化程度更高，更易做白名单校验（表名/列名/关键字），图查询语言（如 Cypher）校验更难。

## 已知限制

### 1. 不支持多意图查询

当前系统单条问句仅识别一个意图。当问句包含多个意图关键词时（如「比亚迪的关联方里有没有担保」同时包含"关联方"和"担保"），分类器按关键词检查顺序返回第一个匹配的意图，而非返回多个意图。

留出集 80% / 90% 的数字**包含此限制**，是真实能力水平。6 条多意图失败占留出集意图分类失败总数的 75%。

正确做法是多意图识别 + 分别执行 + 结果合并，属功能扩展而非缺陷修复。不通过调整关键词优先级修复——这是零和交换，让一类通过必然让另一类失败。

### 2. 规则槽位抽取的公司名匹配限制

`rule_slots.py` 的 `_COMPANY_NAME` 正则要求公司名以已知后缀结尾（股份有限公司/有限公司/集团/控股/投资/银行/保险/医药/时代/绿能/精密）。不带后缀的简称（如"比亚迪"、"茅台"、"中国平安"、"五粮液"）无法匹配。

这导致 10 条静默错误（规则抽取出了值但值来自 context_code 而非问句中的公司名）和 2 条覆盖失败（无 context_code 时无法抽取）。正确率 73%。

静默错误发生条件：问句含不带后缀的公司简称 + 有 context_code → 规则未匹配到公司名，回退到 context_code。结果在多数情况下是正确的（因为 context_code 就是用户正在查看的公司），但严格来说规则抽取的不是问句中的公司名。

### 3. uncertain 阈值诊断

留出集 2 条错别字（"关联防"、"关连方"）在意图分类测试中标记为失败（期望 Q1, 规则返回 Q7）。诊断结论：

- 规则分类器**正确地**将这两条标记为 `uncertain=True`（confidence=0.3, intent=Q7）
- `uncertain=True` 触发 LLM 兜底路径，LLM 在 `classify_and_extract` 中正确分类为 Q1
- 端到端测试中这两条**全部通过**（HO-31 和 HO-34）
- **uncertain 阈值不需要调整**——规则无法处理错别字是预期行为，LLM 兜底是设计内的正确路径
- 留出集意图分类的 80% 反映的是规则-only 准确率，端到端 90% 包含 LLM 修正
